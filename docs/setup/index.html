Run your own copy

From an empty virtual machine to a student sitting their first interview. About an hour of work, most of it spent waiting for packages to install and for DNS to propagate.

Before you read further

Every command on this page was run, in this order, against a machine that started empty. The outputs shown are real. Where something went wrong the first time, this guide says so rather than pretending the path was clean.

What you need first

Five things, and the platform can produce none of them for you. Get them before you start — the provisioning script stops and tells you what is missing, but it is a duller hour if you collect them as you go.

A server

Debian 12 or Ubuntu 22.04 and newer, 2 GB of memory, root access over SSH with a key. Any provider. Nothing here is specific to one.

≈ €5 / month

A name for it

A domain or subdomain you control the DNS for. rise.your-school.example is perfectly good; it does not need its own domain.

≈ €10 / year

A mailbox to send from

Any SMTP server. Prefer the school's own: an invitation asking a student to set a password should arrive from an address they already recognise.

Usually already have one

A language model key

Scaleway's Generative APIs by default — the model runs in Paris, so no student answer leaves the EU. Billed per token, not per seat.

≈ €0.01 per interview

A Google service account

Optional. Only if teachers will author interviews in Google Sheets. Content can be imported from CSV instead.

Free

On the per-interview figure: at Scaleway's list price the default model costs €0.25 per million tokens in and €1.50 per million out, and a ten-question interview — each answer scored against its rubric, plus a closing summary — comes to roughly one euro cent. You do not have to take that on trust. The platform records the token count and the computed cost of every single model call, so after a week of real use you can read your own number instead of ours.

Step 1

Point the name at the machine

Do this first and do it before anything else, because the provisioning script asks a certificate authority to verify the name — and that check fails, irreversibly for an hour or so, if the name does not yet resolve to this machine.

At your DNS provider, one record:

TypeA
Namerise — or @ if you are using a whole domain
Valuethe server's IPv4 address
TTLwhatever the default is

Then wait, and check from somewhere that is not your own laptop — your laptop may have cached the answer from before the record existed:

dig +short rise.your-school.example

When that prints your server's address, carry on. If it prints nothing after twenty minutes, the record is wrong somewhere; no amount of waiting fixes a typo.

Step 2

Run the provisioning script

One script takes the machine from nothing to a running installation: system packages, an unprivileged deploy user, PostgreSQL, the application under systemd, nginx, a TLS certificate that renews itself, log rotation, and a daily database backup.

Fetch it and read it before you run it. It runs as root, it is 590 lines, and every section says what it is about to do and why.

# on the server, as root
curl -fsSLO https://raw.githubusercontent.com/tehnickazr/RISE-Project/main/deploy/provision-production.sh
less provision-production.sh
Set your own domain

The script's built-in defaults are ours — app.riseproject.space, and our repository. Left alone it will cheerfully request a certificate for a name you do not own and fail. Pass RISE_DOMAIN.

RISE_DOMAIN=rise.your-school.example \
RISE_ADMIN_EMAIL=admin@your-school.example \
bash provision-production.sh

Four environment variables change its behaviour. The rest is fixed on purpose, so that two installations look the same when something needs debugging:

RISE_DOMAINThe hostname the platform answers on. Always set this.
RISE_ADMIN_EMAILWhere the certificate authority sends expiry warnings, and the default from-address for mail.
RISE_REPOA different clone URL — your own fork, for instance.
RISE_BRANCHA branch other than main.

It takes about eight minutes, nearly all of it apt. It prints every step, and it says what it skipped as clearly as what it did — because it is designed to be run again. Run it a second time after fixing something and it will not overwrite the database, the environment file, or the certificate.

What it deliberately will not do

It does not invent the secrets you have to obtain, it does not create the first administrator, and it does not switch on automatic deployment. A script that wrote plausible-looking placeholder keys would hand you a server that starts and then fails at the first interview, which is a worse failure than one that refuses to start.

It ends by printing what still needs a human. That list is the rest of this page.

Step 3

Fill in the four secrets

The environment file lives at /opt/apps/rise/shared/.env, owned by the deploy user and readable by nobody else. It is outside the application directory deliberately: a deploy replaces the checkout, and the secrets must survive that.

ssh root@rise.your-school.example
nano /opt/apps/rise/shared/.env

Everything that could be generated already has been — the session secret, the database password, the public origin. Four lines are marked NEEDS VALUE.

SCW_SECRET_KEY — the language model

In the Scaleway console: Identity and Access Management → API keys → Generate an API key. Name it for this server, so that revoking it later is not an act of archaeology.

  • Only the secret key matters. The access key, the project ID and the organisation ID belong to other Scaleway products and the platform never reads them.
  • It is shown once. Paste it straight into the environment file.
  • Note the expiry date in a calendar. Many organisations cap key lifetime at one year, and an expired key does not degrade gracefully — every interview simply stops working, on a Tuesday, a year after you have forgotten doing this.

SMTP_PASS — and the three lines above it

The script fills the mail settings with the defaults for the host we used. If your mail is elsewhere, correct SMTP_HOST, SMTP_PORT and SMTP_USER as well as the password. Port 587 is STARTTLS, 465 is implicit TLS; the platform infers which from the port. Port 25 is blocked outbound by nearly every provider and will only ever time out.

Quote the password

This cost us an afternoon. Mail passwords often contain |, &, $ or #. systemd reads this file literally and does not care — but the deploy script reads it with source, where an unquoted | is a pipe and the rest of the password is a command. Write SMTP_PASS='the-password', in single quotes, always.

GOOGLE_SERVICE_ACCOUNT_EMAIL and GOOGLE_PRIVATE_KEY

Only if teachers will author content in Google Sheets. Create a service account in the Google Cloud console, enable the Sheets API, download a JSON key, and share each school's spreadsheet with the service account's address as Viewer — the platform never writes to a sheet. Leave both blank to start with; content imports from CSV without them.

Then restart, and confirm it came back:

systemctl restart rise
systemctl status rise --no-pager
Step 4

Prove that mail leaves the building

Do this before mail is an invitation to a fourteen-year-old. The usual failure is not a wrong password but a blocked port, and from your laptop the two look identical — which is why this runs on the server.

cd /opt/apps/rise/current/backend
sudo -u deploy node --env-file=/opt/apps/rise/shared/.env \
  scripts/check-mail.mjs you@your-school.example

It prints the configuration it resolved, opens the connection, authenticates, and sends one plain message. Go and look in the inbox. And in the spam folder — if it landed there, fix SPF and DKIM on the sending domain now, because invitations that go to spam are indistinguishable from invitations that were never sent, and you will spend a week not knowing which.

Step 5

Create the first administrator

There is no default account and no default password. One is generated here, shown once, and stored only as a hash — which is also why this is a command and not a line in the database schema, where a password would live in version control forever.

cd /opt/apps/rise/current/backend
sudo -u deploy node --env-file=/opt/apps/rise/shared/.env \
  scripts/create-super-admin.mjs admin@your-school.example "Platform administrator"
  super administrator created
  ---------------------------
  email    admin@your-school.example
  password Xq4t9Fbn2wKpLmR7vZ

  Shown once. Change it after signing in.

Write it down before you close the terminal. There is no second copy. The way back, if you lose it, is a password-reset link to that mailbox — which is one more reason step 4 comes before this one.

What this account can and cannot do

It creates schools and invites their administrators. It cannot read a single student's transcript, at any school, ever — not because it is forbidden by a permission check, but because no endpoint exists that would return one. The same is true of the school's own administrator. Only the student, and teachers at that student's own school, can see an interview.

Step 6

Create the school

Everything from here happens in a browser. Sign in at https://rise.your-school.example and change that generated password on the account page straight away.

  1. Create the organisation. Name, country, and a default language — the default language is what invitations are written in, so it is worth getting right rather than fixing thirty times.
  2. Invite its administrator from the organisation's row. This is the first real message the platform sends to a real person.
  3. Set the platform support contact while you are here. Until it is set, the help page a student sees carries only their school's entry.

Then sign out, open the invitation, and set the password as that school administrator. It is tempting to skip this and stay signed in as the platform administrator — don't. It is the exact path every teacher will take, and it is the one most likely to have a rough edge on your particular mail setup.

Step 7

Give it something to interview about

An installation with no content is a working installation with nothing to do. As the school's administrator, in Settings:

  • Content source — point the school at its own spreadsheet and press import. Four tabs: scenarios, questions, rubrics, glossary. Start from the sample CSVs in seed/sheets/ — four trades, five questions each — and replace them with your own.
  • Privacy notice — the school's own controller, data protection officer, lawful basis and retention periods. Until these are filled in the gaps are visible in the notice students read, which is deliberate.
  • Help and contacts — who a student writes to when something breaks.

Editing the spreadsheet changes nothing until somebody presses import. That is what stops a half-finished edit reaching a class mid-lesson. Imports are versioned, and every interview records the version it was taken against, so changing a question can never alter an interview already sat.

Step 8

Three things before students arrive

A daily backup is already running — the script took one during provisioning and repeats it at 02:30. It writes to /var/backups/rise on this machine, which answers somebody deleted the wrong class on Tuesday. It does not answer the disk died, because the database and every dump are on that same disk.

1. Add an off-site copy

Put any S3-compatible bucket in /etc/rise/backup.env and run it once by hand. Backups are encrypted on this machine before they leave it, so the storage provider never holds anything readable.

nano /etc/rise/backup.env
/usr/local/bin/rise-backup && restic snapshots

Use a key that can write but not delete. A server able to destroy its own backup history is one bad command away from having none.

Then copy the password off the server

RESTIC_PASSWORD in that same file was generated during provisioning, and it is the only thing that makes those backups readable — including by you. It currently lives on the machine the backups exist to protect. Put it in a password manager now.

2. Switch on machine snapshots

In your hosting provider's panel, weekly at least. Nothing running on the host can do this for itself, and it answers the failure a database dump cannot: the machine you restore onto.

3. Check that yesterday's backup happened

Not today's — you just watched today's. The one that ran unattended.

systemctl list-timers rise-backup --no-pager
tail /var/log/rise/backup.log
After

Deploying changes

Once it is running, updating is one command, run deliberately by a person:

ssh deploy@rise.your-school.example \
  'bash /opt/apps/rise/current/deploy/deploy-production.sh'

It pulls, installs, builds the frontend, applies any pending database migrations and restarts the service. There is a timer in the repository that would do this every minute, and it is left switched off on a production host on purpose: on a machine holding interview transcripts, what is running should change because somebody decided it should.

When something is wrong

journalctl -u rise -n 100Why the service will not start. Start here, always.
tail -f /var/log/rise/app.logWhat the application is doing while a student uses it.
nginx -tAfter touching a vhost, before reloading and finding out the hard way.
certbot certificatesWhat is issued and when it expires. Renewal is automatic; verifying it happened is not.

Three failures account for most of what goes wrong on a first install: a TLS certificate that was never issued because DNS had not propagated when the script ran (fix the record, run the script again — it is safe); mail that authenticates but is silently filed as spam (SPF and DKIM); and a language-model key that was pasted with a trailing newline or a wrapped line (the platform starts fine and fails at the first answer).

If you get stuck

The architecture document covers tenancy, auditing and retention — the sections your data protection officer will ask about. Questions, corrections and patches are welcome at the repository; if a step on this page did not work for you, that is a bug in the page and worth reporting as one.
